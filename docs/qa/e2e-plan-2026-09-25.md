# End-to-end test plan — 2026-09-25

Deep testing of the product **from the UI**, against the dev server on :3000 and the real
development database. Two instruments, deliberately: the founder's real Chrome (the Claude
extension, signed in as the founder) drives the journey a consultant actually sees, one surface at
a time; headless Playwright drivers run in parallel for breadth, one per area, each owning a
disjoint slice of the code so fixes cannot collide. Every finding is fixed on the fly by the owner
of that slice or routed to whoever owns it; nothing is marked passed on inspection.

Status legend: ☐ not run · ✅ passed · ❌ failed (issue linked) · 🔧 fixed and re-run · ⏭ blocked

## Findings

Appended by owners as they go: `- [area#] symptom → cause → fix (commit) or routed to <owner>`.

- [A5] copy said "Shown once" for the invite temp password; it is a 60-second cookie in the inviter's browser → copy now says so (this commit). Not a defect: the scope is the control.
- [A9] there is no way for a consultant to change their own password, and an invited member keeps the temporary one → **feature gap, routed to the founder** (small: a password form on settings + bcrypt rehash; not built without a decision).
- [A·env] one consultant-visible 500 ("Transaction already closed" after 6.5s) under load average 28–33 with four Chromium drivers on one laptop → environment, not product; worth remembering for a 512 MB Render Starter running PDF renders — that is what the box-size risk looks like.
- [A·harness] `submitAndSettle` hard-coded 30s (routed by driver B) → now 60s default, `CLOSECHECK_E2E_ACTION_TIMEOUT_MS` overrides; React 19 dev-only `performance.measure` error (routed by driver C) → filtered in `collectPageErrors`.

- [B·harness] `helpers/browser.ts` hard-codes 30s in `submitAndSettle`/`submitExpectingRefusal`; under a shared server at load 45 that budget produced false failures on three rows → not a product bug → routed: tests/integration/helpers/browser.ts, main session (outside slice B). Suite 2 carries local 120s copies.
- [B7] evidence downloads are `application/octet-stream`, not the stored type → deliberate stored-XSS defence documented in the route → pinned in the test rather than "fixed".
- [B10] a webhook receiver on 127.0.0.1 cannot receive: `isDeliverableWebhookUrl` refuses loopback → by design; delivery/payload shape remains covered by `webhook-payload.itest.ts` against an unroutable host.
- [B·general] no product defects found in area B; every row verified with before/after database state, not page text alone.
- [D5/D3 → knob, default kept] every page and action opens a 5s interactive transaction, starting with the session check, so a few-second event-loop stall 500s every user → tried 20s; the full suite then hung one row behind queued requests (POSTs 24–94s, zero transaction errors) that passes at 5s (176/176). The budget is now an env knob for an operator with a measured stall; the default stays Prisma's. Measured both ways.
- [D → fixed] `runOrRedirect` forwarded raw exception text — Prisma errors, absolute paths, `.next` chunk names — into `?error=` and the page → only a plain `Error` this application wrote reaches the consultant; everything else becomes one generic sentence and still lands in error_events (`userFacingMessage`, unit-tested).
- [D6 → fixed] the three overflowing controls (template select, evidence attach row, logo-upload form) shrink and wrap at 400px; the D6 test is one strict half again.
- [C3-semantics] a portal page view logs a DOCUMENT row for its own embedded PDF fetch; `collapseEmbeddedFetches` (unit-tested in `src/lib/portal/accessHistory.test.ts`) removes it for display, so "Report downloaded" appears only for an explicit fetch. Driver C's run included an explicit fetch, which is why it saw both. Not re-verified in the UI here.
- [A9, open] no password-change surface — the founder's call.
- [real browser, not done] the founder's Chrome refused localhost before any request was made (extension site allowlist); the visual walk of the consultant's journey is still owed once `http://localhost:3000` is allowed.
- [harness] the first request to a route after its source changes is a `next dev` recompile — 55–81s under load, tens of seconds idle — and a row that visits several such routes can overrun its own budget while every step still succeeds. Two B11 "timeouts" after the phone-width edits were this; the row passed at a 15s action budget once compiled. Run a changed route once before trusting a timing.
- [ALL · production build → fixed] every sign-in and sign-up on a production build (`next start`) ended at `/api/auth/callback/credentials` with a 500 and `[auth][error] UntrustedHost`; no session was issued, and 38 rows across 11 files failed at their first signed-in interaction. `next dev` trusts the host implicitly, so nothing local ever showed it; CI's `npm start` job was red for the same reason. → `trustHost: true` in the Auth.js config, with the reasoning; the suite is re-run against the production build (see deployment.md for the recipe). **This would have been the first real sign-up on Render.**
- [B11 → dev artefact] flaky in the full matrix on `next dev` (click never fires within the locator budget; the server answers every POST in under 2s), solid alone, and **passes in the full matrix against the production build**. Not a product defect; the full-matrix harness runs against the production build from here (recipe in deployment.md).
- [production build · storage] with `NODE_ENV=production`, no bucket and no acknowledgement, every upload, report and download refused (8 refusals in the server log) and every storage-touching row failed — the guard doing its job; the harness recipe now sets `STORAGE_ACKNOWLEDGE_LOCAL=true`. Expected on Render only if the five `STORAGE_S3_*` values are missing, which `verify:deployment` reports first.
- [D2/D3 → real defect, fixed] the "shown once" reveal of a new API key or webhook secret was on screen for **~50 ms on a production build** (one 50 ms sample at +63 ms) and ~100 ms on `next dev`: `RevealOnce` called a server action on mount to expire the cookie, every server-action call re-renders the route, the re-render found no cookie and unmounted the reveal. The dev-based test read it inside the window and passed; the production run could not. Nobody could have copied the secret. Fixed by keeping the value in client state across the refresh and mounting the component unconditionally; measured again after the fix.
- [D2/D3 · cookies over HTTP → also fixed] the one-time reveals (API key, webhook secret, invite temp password) set their cookie `secure` whenever `NODE_ENV=production`, so a production build served over plain HTTP — CI's `npm start`, the local recipe — never renders them: the browser drops the cookie. The rule is now "secure iff the public URL is https" (the rule Auth.js uses for its own cookies), with a production fallback to secure when no URL is set. Render is https; nothing changes there.
- [production build · totals] first run 38 failed / 115 passed (UntrustedHost); after `trustHost` 8 failed (storage guard); after the acknowledgement 2 failed / 174 passed (the reveal, above); after the reveal fix **176 / 176**, with the reveal measured on screen for the full 4 s window (79 of 80 samples) and gone after a reload.
- [CI · environment → fixed] CI runs the production build with no Stripe keys, no storage acknowledgement and `TRUSTED_PROXY_HOPS=0`; the drivers' suites assumed the local `.env`. CI now acknowledges local storage (its runner disk is what the suite needs); rows that need Stripe on the server (B4, D1, the credit notice in the journey, B10's credit stamp) skip or assert the unconfigured state *with the reason printed*; the lockout leg (A2) and the portal view's address hash (C3) are asserted only where a forwarded address is trusted. Reproduced locally against a production server configured exactly like CI: 176 rows → 0 failures with 10 reasoned skips.
- [CI · static job → fixed] `layout.tsx` used `LayoutProps`, a global Next writes into `.next/types` on build — present on any machine that has built, absent on a runner that type-checks first. Replaced by an explicit props type.
- [B10 · not a defect, twice] on CI the webhook WAS delivered — the receiver got it — and the row read `lastSuccessAt` before the dispatcher's success write landed; it now waits for that write. Earlier, on the local production build, the receiver's failure was recorded only after the dispatcher's full worst case — three 5 s attempts plus 2 s and 4 s back-off, 21 s — and the row waited 15 s. It waits past the worst case now. Post-response work is not dropped in production; verified by the row passing, not assumed.
- [CI · green] run 36136575933 for `b7f1544`: "Lint, types, unit tests" and "Integration and browser journey" both succeeded — the first fully green run since this plan began. Every earlier push of the day was red on one job or both, for reasons nobody had read because each push cancelled the run before it.
